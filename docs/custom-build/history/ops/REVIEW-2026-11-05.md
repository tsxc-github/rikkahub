## F1 / P1：去重查的是展示历史，不是模型实际上下文

**位置**：`OpsReadDedup.kt:28-47`，`app/.../data/ai/ChatRequestFactory.kt:232`，`ai/src/main/java/me/rerere/ai/ui/Message.kt:187-190,204-216`，`app/.../data/model/Conversation.kt:51-54`。

`maybeDedupRead()` 扫描数据库 `conversation.currentMessages` 的最近 200 条消息，只要曾出现同样输出就返回 `body skipped`。但 `currentMessages` 只是选中分支的展示历史；构建请求时另调用 `messages.limitContext(assistant.contextMessageLimit)`：

1. 丢弃最后一个压缩检查点之前的消息（这些仍保留给用户查看）；
2. 再按消息数限制裁剪。

因此旧 read 结果保留在数据库、却不在请求中时，仍会去重成功。模型会得到一个不存在于其当前上下文中的 toolCallId，且没有可读取的 ref。这直接否定了 PLAN §9「压缩会让判定自然失败」的安全保证。

**触发**：读一个返回文本 ≥4000 字符的窗口；跨轮后压缩/触发 contextMessageLimit，但旧输出仍在最近 200 条展示历史中；再次读相同窗口。结果是正文被省略。

**修复建议**：短期禁用 `maybeDedupRead`。若保留，必须以实际请求投影为依据，且考虑新 tool 结果追加后下一次请求可能再次裁剪；无法保证旧正文仍可见时，返回全文或可独立取回的 ref。不能仅给当前函数加一个「排除压缩前历史」就认为所有裁剪问题解决。

**验证性质**：完整调用链静态证明；本次未在 Android 上实际执行压缩场景。

## F2 / P2：workspace_result 的分页无法取回中等长行的尾部

**位置**：`OpsResultStore.kt:30-32,134-153,67`，`OpsReadWindow.kt:70-72,85-89`。

存储仅对 **>2000 字符**的行折行，但分页渲染会把每行 **>400 字符**的部分直接截掉，并把下一 offset 指向下一物理行。

- 401～2000 字符的行：尾部虽然在 ref 文件中，但任何行 offset 都无法通过 `workspace_result` 取回。
- >2000 字符的行：第一块是 400 字符正文 **加** `[!wrapped ...]`，渲染时折行标记本身又被 400 字符上限裁掉。

这不是正常的「还有下一页」，而是分页 API 有不可达数据。用户看到的 `(+N chars)` 至少能提示裁剪，但 API 没有取回它们的参数。

**修复建议**：结果引用分页与普通文件窗口分开渲染。ref 输出按总页预算停，不再丢弃行内字符；或把长行切为所有块均可寻址、长度包含标记也不超过渲染上限的 continuation 行。

**复现**：`review/reproduce.py` 用源码相同的阈值/判据验证 401、1200、2000 字符的行尾均不可由行 offset 取回。不是 Kotlin/JVM 单测。

## F3 / P2：容量淘汰方向反了，新 ref 可能刚生成就失效

**位置**：`OpsResultStore.kt:45-52,71-79`。

`prune()` 先 `sortedByDescending(lastModified)`，再从前往后在 `total > KEEP_BYTES` 时删文件。所以容量超限时先删最新文件，而非最旧文件；且 `put()` 先写入再 prune，最后仍返回可能已被删掉的 ref。

**例**：旧引用 120 MiB、新引用 100 MiB，总计 220 MiB。实现会删除新的 100 MiB、保留旧的 120 MiB，随后返回新 ref；立即翻页即 expired。200 个数量上限本身按索引清旧的方向是对的，出错的是总字节数条件。多会话竞态会进一步加剧，但不是本条成立的前提。

**修复建议**：统一按旧到新淘汰，并保护当前新写的 ref；单个输出超过容量时明确限制/报错，而非返回一个已不存在的引用。必要时对写入/清理加锁。

**复现**：脚本按源码同一排序与删除谓词计算上述元数据，未在手机制造 220 MiB 文件。

## F4 / P2：grep 把经过隐藏裁剪的数量当成全部命中数

**位置**：`OpsSearchTools.kt:139,145,151,177-180,196-200`。

至少有三层裁剪：rg/grep 每文件 `max-count 8`；shell 只 `head -n 400`；Kotlin 再套 max/字符预算。最后的 `N matched` 只是经过前两层裁剪后的 `hits.size`，没有全量语义。

**真实 shell 复现**：单文件写 30 行 `needle`，执行源码相同 rg 命令只返回 8 行。Kotlin 汇总因此是 `[hits: 8 shown / 8 matched]`，完全没有 omitted 提示。模型很容易错误认为已找全相关调用点。

400 行 head 截断亦无独立 sentinel，`max=500` 也不能检测第 401 行存在。

**修复建议**：不假装做全量计数。返回 collected/shown，并明确 per-file/global cap 的存在；用 N+1 或独立截断标志证明是否还有更多。需要全量时另行显式请求，避免为计数无界收集。

## F5 / P2：glob 被两套不同语法重复解释，合法 rg 命中会被删掉

**位置**：`OpsSearchTools.kt:59-75,142,180`。

rg 已经用 `-g` 做了过滤，但 Kotlin 随后仍无条件执行自制 `wildcardMatch()`。后者只支持 `*`/`?`，且把其余 glob 语法当字面量，和 rg 不等价。

**真实 rg + 原谓词镜像复现**：

- `!*.md`：rg 正常返回 a.kt，Kotlin 后过滤全部删除，最终误报 no match。
- `**/*.kt`：rg 会包含搜索根目录的 a.kt，Kotlin 要求 `/` 必须存在，误删根目录文件。
- 字符类/花括号等也不由该匹配器正确支持。

**修复建议**：rg 分支不要二次解释 glob。fallback 若只支持较小语法子集，应明示或拒绝不支持的语法；不要默默给出 no match。

## F6 / P2：无 rg 时先 head 再 glob，可能误报完全无匹配

**位置**：`OpsSearchTools.kt:145-151,177-185`。

fallback 的 grep 不带 glob，先收所有文件命中，再 head 400，最后 Kotlin 筛文件名。若前 400 行来自不符合 glob 的文件，真正符合 glob 的命中在第 401 行以后，结果将是 no match，而不是 omitted。

**复现**：脚本使用真实 grep，显式有序输入模拟目录枚举：前 408 个命中来自 md，最后一个来自 kt。head 后按 `*.kt` 过滤得到空，但确有 kt 命中。显式输入只用于消除文件系统枚举顺序差异，源码实际接收的是一个目录 path。

**修复建议**：在搜索/计数之前先选符合 glob 的文件（find + 安全参数传递），而非截断后过滤。若达预算时仍无法排除存在匹配，必须返回 incomplete，不能断言 no match。
